## 1. How to Use This Document

- Phases are **dependency-ordered**. Do not begin a phase until its dependencies are met.
- Each phase has explicit **acceptance criteria** — the phase is not done until all criteria pass.
- Tasks use checkboxes. Check them off in `Tracker.md` as they complete (do not edit this file for progress tracking).
- Mark uncertainty with `[DECISION NEEDED]` before starting work that depends on an unresolved decision.
- Phases 0–12 together constitute **MVP delivery**.
- Phase 13–15 are required before MVP can be considered production-ready.
- Phase 16+ is post-MVP.

## 8. Phase 5 — Search Pipeline

**Goal:** A working end-to-end search API endpoint. User sends a query; Marang fans out to sources, normalizes results, and returns a deduplicated, paginated list.

**Dependencies:** Phase 4 (Source Registry + Adapter), Phase 2 (Database).

### Tasks

#### Search Service

- [ ] Implement `SearchService` in `backend/src/search/search.service.ts`:
  - `search(query: string, options: SearchOptions): Promise<SearchResults>`
  - Query normalization (trim, Unicode normalize, lowercase)
  - Fan-out to all `SEARCH`-capable adapters via `Promise.allSettled`
  - Per-source timeout enforcement (5s)
  - Failed sources logged and excluded from results
  - Results collected from fulfilled sources
- [ ] Implement `ResultNormalizer` in `backend/src/search/normalizer.ts`:
  - `normalize(sourceResult: SourceSearchResult): NormalizedSearchResult`
  - Normalize titles, contentType, status, cover URL
- [ ] Implement `DeduplicationService` in `backend/src/search/deduplication.ts`:
  - Group normalized results by normalized title + contentType
  - Merge source mappings for grouped results
- [ ] Implement result ranking (title relevance score, source count)
- [ ] Implement search result caching in Redis (key: `search:{normalizedQuery}:{page}`, TTL: 10 min)

#### Search API

- [ ] Add `GET /api/v1/search` route handler in `backend/src/api/routes/search.ts`
  - Query params: `q` (required), `page` (default 1), `pageSize` (default 20)
  - Input validation via Zod
  - Call `SearchService.search()`
  - Return paginated `{ data: SearchResult[], meta: { page, pageSize, total, sourcesFailed } }`
- [ ] Write unit tests for `ResultNormalizer` with fixture data from first adapter
- [ ] Write unit tests for `DeduplicationService` with overlapping title scenarios
- [ ] Write integration test for `GET /api/v1/search` with mocked adapter

### Acceptance Criteria

- [ ] `GET /api/v1/search?q=naruto` returns a `200` with normalized results
- [ ] Results from multiple sources with the same normalized title are deduplicated to one result
- [ ] A source timeout does not cause the endpoint to hang or return an error — remaining results returned
- [ ] Response includes `meta.sourcesFailed` count when a source fails
- [ ] Second request for same query returns cached results (verify via Redis key inspection)
- [ ] Empty query returns `400 VALIDATION_ERROR`
- [ ] All unit and integration tests pass

### Outputs

- `backend/src/search/search.service.ts`
- `backend/src/search/normalizer.ts`
- `backend/src/search/deduplication.ts`
- `backend/src/api/routes/search.ts`

## 12. Phase 9 — Source Resolution

**Goal:** The source resolver can take a series or chapter request and return the best available source with a usable URL or handoff point.

**Dependencies:** Phase 4 (Source Registry), Phase 6 (Catalog), Phase 8 (Library — for preferred source preference).

### Tasks

- [ ] Implement `ResolutionService` in `backend/src/resolution/resolution.service.ts`:
  - `resolveSeries(seriesId, userId?): Promise<ResolutionResult>`
  - `resolveChapter(chapterId, userId?): Promise<ResolutionResult>`
  - Load `SourceMappings` for the series
  - Filter to registered, enabled, healthy sources with required capability
  - Apply user's `preferredSourceId` if set on their `LibraryEntry`
  - Score and rank remaining sources (health, capability, language)
  - Return top-ranked `ResolutionResult`
  - Throw `ResolutionNoSourceError` if no sources available
- [ ] Implement source health scoring helper:
  - `healthy` → full score
  - `degraded` → reduced score
  - `unhealthy` → excluded entirely
- [ ] Add API routes:
  - `GET /api/v1/resolve/series/:seriesId` — returns `ResolutionResult` for continue-reading
  - `GET /api/v1/resolve/chapter/:chapterId` — returns `ResolutionResult` for specific chapter
- [ ] Add history entry recording to resolution (when a chapter is resolved, record in `ReadingHistory`)
- [ ] Write unit tests for scoring and ranking with multiple source scenarios
- [ ] Write unit tests for failure: all sources unhealthy, source missing capability, no mappings

### Acceptance Criteria

- [ ] Resolving a series with one healthy source returns that source
- [ ] Resolving with a user-preferred source promotes it to first choice
- [ ] Resolving with an unhealthy source excludes it; next source used
